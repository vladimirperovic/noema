# Privacy and data flows

Noema is self-hosted. The operator chooses the server, domain, reverse proxy, storage, backups, and optional external integrations. The project does not run a hosted Noema service and does not receive installation data by default.

## Data stored locally

Depending on enabled modules, Noema stores:

- task titles, dates, priorities, completion, recurrence, subtasks, and source references;
- notes and document content;
- saved links, fetched metadata, and optional locally generated page thumbnails;
- Files names, descriptions, types, sizes, and binary content;
- Building Sites and Inspiration metadata, images, thumbnails, locations, tags, and hotspots;
- document uploads and other managed private binary content;
- optional analytics project configuration from environment variables;
- hashed UI sessions and hashed gallery-share tokens;
- encrypted Google Calendar refresh token;
- encrypted metadata snapshots and optional full encrypted backup archives.

## Encryption at rest

Noema's persistent-storage policy is: **everything entered/uploaded by the user, or generated by Noema from private user data, is encrypted at rest.**

Metadata records are encrypted before storage in SQLite. Compatibility mirrors, sessions, shares, and the Calendar token are encrypted. Files binary objects are encrypted. Managed uploads, gallery originals/thumbnails and generated Links screenshot thumbnails are also stored as ciphertext below `NOEMA_DATA_DIR`.

Large private binary assets use independently authenticated chunks so authorized byte-range reads can be reconstructed without exposing plaintext files in a static/public directory.

This is server-side encryption at rest, not end-to-end encryption. The running Noema process can decrypt authorized content and keeps the unlocked installation data key in process memory while running.

## Browser storage

The UI may keep non-secret preferences and mappings in browser storage, including manual theme choice, page width, font scale, Links card density/view mode, and source-task link mappings.

Authentication uses an HttpOnly session cookie. Gallery sharing uses an HttpOnly share cookie after a valid share URL is opened. Browser scripts cannot read these cookies.

## External requests

Noema may contact external services only when their feature is used or configured:

- Google OAuth and Google Calendar API for read-only calendar events;
- Google Analytics Data API, Search Console, and PageSpeed when Stats is configured;
- OpenStreetMap/Nominatim and map tile providers for location features;
- target websites when link metadata, readable article text, or a local page screenshot is requested;
- remote image/media URLs supplied by users.

External services receive normal HTTP request metadata such as the installation IP address, configured user agent, requested URL, and any service-specific credentials.

Links thumbnail generation is local to the Noema host: the saved URL is opened by the installation's Chromium process. The target website sees the request, but the URL is not sent to a third-party screenshot API. Screenshot plaintext exists only in system temporary processing storage; the persistent thumbnail is encrypted.

## Temporary processing

Some operations necessarily require plaintext bytes while they execute. For example, ZIP creation must stage selected originals, and an external media/browser process may need a temporary output file. Noema keeps these transient files in isolated system temporary storage and removes them after the operation. They are not the persistent source of truth.

## Calendar credentials

OAuth client credentials usually come from environment variables. A refresh token obtained through the browser flow is encrypted in `google-token.enc`. OAuth state is short-lived and bound to the administrator session that initiated the flow.

## Public gallery links

Gallery links contain a high-entropy random token. Only its SHA-256 hash is stored. A link has an expiration time, can be revoked, and may be restricted to a gallery module or album.

Anyone who possesses an unexpired link can access its allowed gallery content. The encrypted media gateway applies that authorization when serving bytes; encryption does not replace access control.

## Files and generated media

Files is a private authenticated module. File metadata is included in portable metadata backups, but binary content is not. Full `.noema` archives include both metadata and encrypted binary content.

Generated Links thumbnails and gallery media are also private installation data. Portable metadata may reference them but does not include their bytes; full archives include their encrypted persistent directories.

## Logs

Application logs report startup, migration, configuration, and operational errors. They should not intentionally include passwords, bearer tokens, session/share tokens, encryption keys, file content, or screenshot pixels. Reverse proxies and hosting platforms may maintain their own access logs.

## Deletion and retention

Deleting a record removes it from the active encrypted collection and refreshes its mirror. Managed binary deletion removes the corresponding ciphertext file. Backups remain separate copies and must be expired/destroyed according to the operator's retention policy.

## Backups

Portable JSON contains readable metadata and should be protected like the original records. Full `.noema` archives contain the complete persistent data directory, whose private content is already encrypted at rest, and then add a separate archive-encryption layer using `NOEMA_BACKUP_PASSWORD`.

Losing the installation `master.key` can make persistent application data unrecoverable even if the UI password is known; losing the backup password can make an off-site full archive unrecoverable. Protect both recovery paths appropriately.

## Operator responsibilities

Operators are responsible for legal basis, consent, retention, TLS, host security, reverse-proxy logs, access control, third-party integrations, target-site terms when generating screenshots, and secure disposal of backups and storage media.
