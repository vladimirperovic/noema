# Privacy and data flows

Noema is self-hosted. The operator chooses the server, domain, reverse proxy, storage, backups and optional external integrations. The project does not operate a hosted Noema service and does not receive installation data by default.

## Data stored locally

Depending on enabled modules, Noema stores:

- task titles, dates, priorities, completion, recurrence, subtasks and source references;
- Notes and Document content;
- saved Links and fetched metadata;
- existing locally stored Links thumbnails;
- Files names, descriptions, types, sizes and binary content;
- Building Sites and Inspiration metadata, images, thumbnails, locations, tags and hotspots;
- document uploads and other managed private binary content;
- optional analytics configuration from environment variables;
- hashed browser-session tokens and hashed gallery-share tokens with encrypted metadata;
- encrypted Google Calendar refresh-token state;
- encrypted metadata snapshots and optional full encrypted backup archives.

## Encryption at rest

Noema's persistent-storage policy is:

> **Everything entered/uploaded by the user, or generated by Noema from private user data, is encrypted at rest.**

Metadata records are encrypted before SQLite storage. Compatibility mirrors, sessions, shares and the Calendar token are encrypted. Files binary objects are encrypted. Managed uploads and gallery originals/thumbnails are stored as ciphertext below `NOEMA_DATA_DIR`.

Large managed assets use independently authenticated chunks so authorized byte-range reads can be reconstructed without exposing a plaintext persistent file in the public/static tree.

This is server-side encryption at rest, not end-to-end encryption. The running Noema process can decrypt authorized content and holds the unlocked installation data key in process memory while running.

## Browser storage

The UI may keep non-secret preferences in browser storage, including theme, page width, font scale and module-specific view preferences.

Authentication uses an HttpOnly session cookie. Gallery sharing uses an HttpOnly share cookie after a valid share URL is opened. Browser scripts cannot read these cookies.

### Service Worker cache

The Service Worker is intentionally restricted to an explicit allow-list of source-controlled, data-free shell assets.

It does **not** intentionally persist API responses, Files, uploads, gallery media, thumbnails, backup responses or other authenticated/private content in Cache Storage. Sensitive routes are network-only.

When the security cache version changes, historical Noema caches are deleted during Service Worker activation.

## External requests

Noema may contact external services only when their feature is used/configured:

- Google OAuth and Google Calendar API for read-only calendar events;
- Google Analytics Data API, Search Console and PageSpeed when Stats is configured;
- OpenStreetMap/Nominatim and map tile providers for location features;
- target websites when link metadata/readable article text is requested;
- remote image/media URLs explicitly supplied by the user where supported.

External services receive normal HTTP request metadata such as the installation IP address, configured user agent, requested URL and service-specific credentials where required.

### Link thumbnails

Automatic Chromium-based thumbnail generation is disabled in the standard Noema process/container. Existing encrypted thumbnails can still be served.

The generation endpoint fails closed until a separately isolated browser renderer with strict sandbox/network-egress controls exists. This means normal Noema operation does not open saved user URLs in a general-purpose browser process merely to create screenshots.

## Temporary processing

Some operations necessarily require plaintext bytes while they execute. For example, ZIP creation may stage selected originals in isolated system temporary storage. Noema removes temporary staging after the operation and does not treat it as persistent source-of-truth storage.

## Calendar credentials

OAuth client credentials normally come from environment variables. A refresh token obtained through the browser flow is encrypted at rest. OAuth state is short-lived and bound to the administrator session that initiated the flow.

## Public gallery links

Gallery links contain a high-entropy random token. Only its SHA-256 hash is stored. A link has an expiration time, can be revoked and may be restricted to a gallery module/album.

Anyone who possesses a still-valid share URL is authorized for its configured scope. The encrypted media gateway applies that scope when serving bytes; encryption does not replace access control.

## Files and generated media

Files is a private authenticated module. File metadata is included in portable metadata backups, but binary content is not. Full `.noema` archives include both metadata and encrypted binary content.

Gallery media and existing generated Links thumbnails are private installation data. Portable metadata may reference binary assets but does not contain their bytes; full archives include their encrypted persistent directories.

## Public repository screenshots

Screenshots published in the repository are generated from a clean test checkout using neutral demo data.

`scripts/capture-screenshots.mjs` refuses to run when the repository `data/` directory is non-empty, starts a temporary test instance, seeds generic records, captures UI pages and then removes the temporary data directory. Real deployment content is not required or intended for public screenshots.

## Logs

Application logs report startup, migration, configuration and operational errors. They should not intentionally include passwords, bearer/session/share tokens, encryption keys, File contents or private media bytes. Reverse proxies and hosting platforms may maintain separate access/deployment logs.

## Deletion and retention

Deleting a record removes it from active encrypted storage according to the module's persistence behavior. Managed binary deletion removes the corresponding ciphertext file. Backups remain independent copies and must be expired/destroyed according to the operator's retention policy.

## Backups

Portable JSON contains readable metadata and should be protected like the original records. Full `.noema` archives contain the complete persistent data directory and then add a separate archive-encryption layer using `NOEMA_BACKUP_PASSWORD`.

Losing the installation `master.key` can make persistent application data unrecoverable even if the UI password is known; losing the backup password can make an off-site full archive unrecoverable. Protect both recovery paths.

## Operator responsibilities

Operators are responsible for legal basis, consent, retention, TLS, host security, reverse-proxy logs, access control, third-party integrations and secure disposal of backups/storage media.
