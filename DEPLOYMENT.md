# Deployment

## Supported runtime

Noema requires Node.js 22.16 or newer because it uses the built-in `node:sqlite` module. The provided Docker image uses **Node 24.19.0 on Alpine 3.24** and includes only the runtime tools needed by Noema: `curl`, `su-exec`, `zip` and `unzip`.

Browser-based Links thumbnail generation is intentionally disabled in the standard container; Chromium is not part of the runtime image.

Persistent state must be mounted at `NOEMA_DATA_DIR` (`/app/data` in the Docker image).

## Required production settings

Noema 0.3 fails closed in production. Unless the explicit development escape hatch is enabled, startup requires:

```dotenv
NODE_ENV=production
PUBLIC_BASE_URL=https://noema.example.com
NOEMA_CORS_ORIGIN=https://noema.example.com
UI_PASSWORD=a-strong-master-password
NOEMA_API_TOKEN=a-long-random-machine-token
NOEMA_BACKUP_PASSWORD=a-different-long-backup-password
```

`UI_PASSWORD` is the single browser master password. It authenticates the UI and protects the random installation data-encryption key stored in wrapped form in `NOEMA_DATA_DIR/master.key`.

`NOEMA_API_TOKEN` is a separate machine credential. Do not reuse `UI_PASSWORD` as the API token.

Existing installations that previously used `ENCRYPTION_KEY` may need to keep it temporarily during migration. After a successful upgrade/login/restart/data validation cycle, remove the legacy variable.

## Authentication boundary

`src/security-gateway.js` is the browser/API gateway. Noema does not use HTTP Basic Auth for the UI and does not emit a `WWW-Authenticate` challenge.

A successful `/login` creates a revocable server-side session. `/logout` revokes that session.

## Persistent encryption policy

Everything entered/uploaded by the user, and private media generated by Noema, remains encrypted at rest in the persistent volume. This includes SQLite payloads, Files binary content, document uploads, gallery media, existing generated Links thumbnails and encrypted OAuth/session/share state.

Legacy plaintext binary objects are automatically migrated during startup. Before migration Noema verifies the current installation key against encrypted SQLite content. Each encrypted replacement is authenticated and compared with the source plaintext SHA-256 before the plaintext rollback copy is removed.

**The first upgraded startup may take longer on installations with many or large private assets. Do not kill the container simply because `/healthz` is delayed.** Startup intentionally waits for migration so a partially converted data directory is not advertised as healthy.

## Docker Compose example

```yaml
services:
  noema:
    build: .
    restart: unless-stopped
    env_file: .env
    ports:
      - "127.0.0.1:3000:3000"
    volumes:
      - noema-data:/app/data

volumes:
  noema-data:
```

Terminate TLS at a reverse proxy and forward to the loopback/private container address.

## Coolify

Recommended settings:

- build pack: **Dockerfile**;
- persistent volume: `/app/data`;
- container port: `3000`;
- health endpoint: `/healthz`;
- include source commit in build when available so `build-version.json` reflects the deployed revision;
- set all production secrets as runtime environment variables, not committed files.

The Docker build intentionally uses isolated test credentials for build-time checks. Deployment secrets should not alter test semantics.

## Reverse proxies

Noema ignores `X-Forwarded-For` unless the immediate peer is listed in `NOEMA_TRUSTED_PROXY_IPS`. Preserve original host/protocol information and configure proxy request limits above the largest upload you intend to support.

## Session and share lifetime

```dotenv
SESSION_IDLE_HOURS=24
SESSION_ABSOLUTE_HOURS=168
GALLERY_SHARE_TTL_DAYS=30
```

Browser sessions are revocable and expire on idle/absolute timers. Gallery links are random, hashed at rest, expiring, revocable and may be scoped to a module/album.

## Links thumbnails

The standard Noema deployment **does not launch Chromium** against saved user URLs. Existing encrypted thumbnails can still be served, but the generation endpoint fails closed with `503` until a separately isolated renderer is implemented.

This is intentional. A browser renderer needs its own sandbox/network-egress boundary because application-level SSRF preflight alone cannot constrain all browser DNS, redirect and subresource behavior.

## Service Worker behavior

The Service Worker caches only an explicit set of source-controlled static shell assets. API responses, Files, uploads, galleries, private media, thumbnails and backups are network-only.

On a security-sensitive Service Worker change, the cache version is bumped and old Noema caches are removed during activation. After an upgrade, a normal reload should activate the new worker; if a browser remains on an old UI shell, unregister the old worker/cache or hard-refresh once.

## Docker build verification

The Dockerfile performs two independent checks:

1. `npm run check` under isolated test configuration with deployment secrets cleared.
2. A strict production startup and `/healthz` probe using test-only valid production credentials and an empty legacy `ENCRYPTION_KEY`.

After verification, npm/corepack/yarn and their bundled dependency trees are removed from the runtime image. A failed test or startup prevents image creation.

## Data directory

Typical contents include:

```text
noema.sqlite
master.key              wrapped installation data-encryption key
*.json                  encrypted compatibility mirrors
files/                  encrypted Files binary data
uploads/                encrypted document uploads
buildingsites/          encrypted Building Sites media
inspirations/           encrypted Inspiration media
link-thumbnails/        encrypted existing Links screenshots
google-token.enc        encrypted Calendar refresh token
snapshots/              encrypted metadata snapshots
```

Do not copy only `noema.sqlite` and assume a complete recovery. Encrypted records and binary assets depend on `master.key` and their persistent directories. The master password alone cannot reconstruct a lost installation key.

## Backups

### Full disaster recovery

Create a password-encrypted archive:

```bash
npm run backup -- /secure/path/noema-backup.noema
```

The command checkpoints SQLite, includes the complete persistent directory, creates integrity metadata and adds a second AES-256-GCM archive layer using `NOEMA_BACKUP_PASSWORD`.

Restore while Noema is stopped:

```bash
npm run restore -- /secure/path/noema-backup.noema /path/to/noema-data
```

Test restores periodically and keep at least one off-site copy.

### Portable metadata

Portable JSON is readable record metadata. It intentionally does not include the complete binary Files/gallery/upload data set or the installation key. Use it for inspection/record migration, not full disaster recovery.

## Upgrades

1. Create and verify a full encrypted backup.
2. Pull/build the new source image.
3. Preserve the complete persistent data volume.
4. If migrating an old installation, keep the existing `ENCRYPTION_KEY` only as long as required for the migration path.
5. Replace the container and allow startup migration to finish.
6. Confirm `/healthz`.
7. Confirm browser login/logout; there should be no browser Basic-auth username/password popup.
8. Validate representative Notes, Files, Links and gallery content.
9. Validate a representative File/gallery original download and backup creation.
10. Restart once more and confirm the same data remains readable.
11. Remove legacy `ENCRYPTION_KEY` only after successful validation.
12. Keep the previous image and pre-upgrade backup until the upgrade is proven.

## Health monitoring

`GET /healthz` is intentionally unauthenticated for container/orchestrator probes and does not expose record data. During first-start encrypted-storage migration the endpoint may remain unavailable until migration completes.
