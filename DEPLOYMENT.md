# Deployment

## Supported runtime

Noema requires Node.js 22.16 or newer because it uses the built-in `node:sqlite` module. The provided Docker image uses Node 24 Alpine and includes `curl`, `zip`, `unzip`, and Chromium for local Links thumbnail generation.

Persistent state must be mounted at `NOEMA_DATA_DIR` (`/app/data` in the Docker image).

## Required production settings

Noema 0.3 fails closed in production. Unless the explicit development escape hatch is enabled, startup requires:

```dotenv
NODE_ENV=production
PUBLIC_BASE_URL=https://noema.example.com
NOEMA_CORS_ORIGIN=https://noema.example.com
UI_PASSWORD=a-strong-master-password
NOEMA_API_TOKEN=a-long-random-machine-token
NOEMA_BACKUP_PASSWORD=a-different-long-backup-password
```

`UI_PASSWORD` is the single Noema master password. It authenticates the browser UI and protects the random installation data-encryption key stored in wrapped form in `NOEMA_DATA_DIR/master.key`.

Existing installations that previously used a separate `ENCRYPTION_KEY` should keep that value for the first startup after upgrading. Sign in once with the normal UI password; Noema validates existing encrypted storage and re-wraps the same data key with that login password. After a successful restart and validation, remove the legacy `ENCRYPTION_KEY`.

## Persistent encryption policy

Everything entered or uploaded by the user, and private media generated by Noema, remains encrypted at rest in the persistent volume. This includes SQLite payloads, Files binary content, document uploads, gallery media, and generated Links thumbnails.

Legacy plaintext binary objects are automatically migrated during startup. Before migration Noema verifies the current installation key against encrypted SQLite content. Each candidate encrypted replacement is fully authenticated and compared to the source plaintext SHA-256 before the plaintext rollback copy is deleted.

**The first upgraded startup may therefore take longer on installations with many/large gallery files. Do not kill the container merely because `/healthz` has not appeared immediately.** Startup intentionally waits for migration so Noema never advertises healthy while a legacy plaintext persistent data set is only partly converted.

## Docker Compose example

```yaml
services:
  noema:
    build: .
    restart: unless-stopped
    env_file: .env
    ports:
      - "127.0.0.1:3000:3000"
    volumes:
      - noema-data:/app/data

volumes:
  noema-data:
```

Terminate TLS at a reverse proxy and forward to the loopback or private container address.

## Reverse proxies

Noema ignores `X-Forwarded-For` unless the immediate peer address is listed in `NOEMA_TRUSTED_PROXY_IPS`. Preserve the original host/protocol information and configure proxy request limits above the largest application upload you intend to support.

## Session and share lifetime

```dotenv
SESSION_IDLE_HOURS=24
SESSION_ABSOLUTE_HOURS=168
GALLERY_SHARE_TTL_DAYS=30
```

Browser sessions are revocable and expire on idle and absolute timers. Gallery links are random, hashed at rest, expiring, revocable, and may be scoped to a module/album. Encrypted gallery bytes still require this authorization; encryption is not a substitute for share scoping.

## Links thumbnails

The Links page can generate screenshots only for saved links that do not already have an image. Docker includes Chromium. For a non-Docker installation, install Chromium/Chrome and use `NOEMA_CHROMIUM_PATH` only when necessary.

The saved target URL passes the centralized SSRF/public-address preflight before Chromium launches. Chromium writes a transient PNG into system temporary storage; Noema encrypts that PNG before it becomes the persistent file in `NOEMA_DATA_DIR/link-thumbnails`.

## Docker build verification

The Dockerfile performs two independent checks:

1. `npm run check` under isolated test configuration. Deployment environment secrets are explicitly cleared before the test command so builder/Coolify variables cannot change test semantics.
2. A strict production startup and `/healthz` probe using the intended one-password model: `UI_PASSWORD` is set and legacy `ENCRYPTION_KEY` is explicitly empty.

A failed test or startup prevents the image from being built.

## Data directory

Typical contents include:

```text
noema.sqlite
master.key              wrapped installation data-encryption key
*.json                  encrypted compatibility mirrors
files/                  encrypted Files binary data
uploads/                encrypted document uploads
buildingsites/          encrypted Building Sites media
inspirations/           encrypted Inspiration media
link-thumbnails/        encrypted local Links screenshots
google-token.enc        encrypted Calendar refresh token
snapshots/              encrypted metadata snapshots
```

Do not copy only `noema.sqlite` and assume a complete recovery. Encrypted records and binary assets depend on `master.key` and their persistent directories. The master password alone cannot reconstruct a lost random installation key.

## Backups

### Full disaster recovery

Create a password-encrypted archive:

```bash
npm run backup -- /secure/path/noema-backup.noema
```

The command checkpoints SQLite, flushes encrypted mirrors, includes the complete persistent directory, creates SHA-256 checksums, and then adds a second AES-256-GCM archive layer using `NOEMA_BACKUP_PASSWORD`.

Restore while Noema is stopped:

```bash
npm run restore -- /secure/path/noema-backup.noema /path/to/noema-data
```

Test restores periodically and keep at least one off-site copy.

### Portable metadata

The Backup page can export readable JSON record metadata. It intentionally does not include binary Files contents, thumbnails/gallery media, document uploads, the SQLite database, or the installation key. Use it for inspection/record migration, not full disaster recovery.

## Upgrades

1. Create and verify a full encrypted backup.
2. Pull the new source/image.
3. If upgrading from the old two-secret model, keep the existing `ENCRYPTION_KEY` for the first startup.
4. Replace the container while preserving the complete data volume.
5. Allow the first startup to finish any legacy binary encryption migration; on a large library this can delay `/healthz`.
6. Sign in once with `UI_PASSWORD` so legacy `master.key` protection can be re-wrapped if still needed.
7. Restart and confirm `/healthz`, login, Notes, Files, Links, galleries, Calendar, and backup download.
8. Verify a representative File/gallery original can still be downloaded and, if used, generate one Links thumbnail.
9. Only after successful validation remove the legacy `ENCRYPTION_KEY`.
10. Keep the previous image and pre-upgrade backup until validation is complete.

## Health monitoring

`GET /healthz` is unauthenticated and intended for container/orchestrator health checks. It does not expose record data. During a first encrypted-storage migration the endpoint intentionally does not become available until migration completes.
