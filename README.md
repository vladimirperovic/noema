# Noema

Noema is a zero-dependency, self-hosted personal workspace built with Node.js, the built-in SQLite module, plain HTML, CSS, and JavaScript. It keeps tasks, notes, documents, links, files, project galleries, calendar events, MCP tools, and OpenAPI routes in one private interface.

## What is included in 0.3

- Yesterday / today / tomorrow task board with priorities, time, subtasks, archive, drag and drop, and stable recurring tasks.
- Notes, documents, links, AI projects, Building Sites, Inspiration, Stats, and a private **Files** library.
- **Private-data encryption at rest:** content entered or uploaded by the user, plus private media generated by Noema, is encrypted before it remains in persistent storage.
- Files metadata is encrypted in SQLite and Files binary content is AES-256-GCM encrypted below `NOEMA_DATA_DIR/files`; maximum file size is 120 MB.
- Document uploads, Building Site/Inspiration originals and thumbnails, and locally generated Links thumbnails are encrypted in persistent storage.
- Source-linked tasks: records from Notes, Documents, Links, Files, galleries, and AI Projects can become read-only tasks that deep-link back to their source.
- One canonical responsive menu, active-page highlighting, light/dark mode, font scaling, and a persistent WIDTH control. The top menu/theme controls stay fixed to the viewport while pages scroll.
- Google Calendar read-only integration with an encrypted refresh token and session-bound OAuth state.
- MCP and OpenAPI endpoints for machine clients.
- Server-side revocable browser sessions, trusted-proxy handling, security headers, login/API rate limits, and expiring gallery-share links.
- Password-encrypted `.noema` disaster-recovery archives with a separate backup password.
- Docker image syntax tests, encryption/storage tests, and a strict production startup smoke test.
- Links visual library with 3–6 card density, compact table mode, one-line titles, click-to-select existing labels while adding, and optional locally generated page thumbnails using headless Chromium.

## Encryption model

Noema follows one storage rule:

> **Everything the user enters, uploads, or Noema generates from private user data is encrypted at rest.**

A random 256-bit installation data key encrypts application data with AES-256-GCM. `UI_PASSWORD` is the single password the user enters: it authenticates the browser UI and protects that random installation key in `NOEMA_DATA_DIR/master.key`. The password itself is not used directly as the AES data key.

This is server-side encryption at rest, not end-to-end encryption. The running Noema process can decrypt content for an authorized request. It protects copied disks, persistent volumes, offline data directories, and similar storage exposure; a compromised running host/process remains outside this protection boundary.

## Requirements

- Node.js 22.16 or newer, or Docker.
- Persistent storage for `NOEMA_DATA_DIR`.
- HTTPS for production.
- `zip` and `unzip` for full encrypted backup/restore outside the provided Docker image.
- Chromium is required only if you want to generate Links page thumbnails outside the provided Docker image. Set `NOEMA_CHROMIUM_PATH` when Chromium is installed in a non-standard location.

## Quick local start

```bash
cp .env.example .env
# Set UI_PASSWORD. It is the single browser master password used for login and
# for protection of Noema's installation data-encryption key.
# For an isolated local test you may also set:
# ALLOW_INSECURE_NO_AUTH=true
npm run check
npm start
```

Open `http://localhost:3000`.

## Production configuration

Production fails closed unless authentication and HTTPS are configured. At minimum set:

```dotenv
NODE_ENV=production
PUBLIC_BASE_URL=https://noema.example.com
NOEMA_CORS_ORIGIN=https://noema.example.com
UI_PASSWORD=replace-with-a-strong-master-password
NOEMA_API_TOKEN=replace-with-a-long-random-token
NOEMA_BACKUP_PASSWORD=replace-with-a-separate-long-backup-password
```

Existing installations that still use a legacy `ENCRYPTION_KEY` should keep it temporarily during migration. After one successful login with the normal `UI_PASSWORD`, Noema re-wraps the existing data key without bulk re-encrypting SQLite records. On upgrade, legacy plaintext binary assets are also migrated in place only after authenticated decryption/hash verification. Remove the legacy variable only after a successful restart and validation.

Do not use `ALLOW_INSECURE_NO_AUTH=true` for an Internet-facing deployment. See [DEPLOYMENT.md](DEPLOYMENT.md) and [SECURITY.md](SECURITY.md).

## Docker

```bash
docker build -t noema .
docker run --rm -p 3000:3000 \
  -v noema-data:/app/data \
  --env-file .env \
  noema
```

The image runs the complete test suite during build and then performs a strict production smoke test before it can be published. Chromium is included in the image for local Links thumbnail generation.

## Data and backups

Primary metadata lives in `NOEMA_DATA_DIR/noema.sqlite`; record payloads are encrypted before entering SQLite. Private binary assets live in dedicated encrypted directories such as `files/`, `uploads/`, `buildingsites/`, `inspirations/`, and `link-thumbnails/`.

Large private assets use independently authenticated chunks so Noema can serve byte ranges (for example video) without loading an entire file into RAM. Plaintext needed by external processors or ZIP creation is staged only in isolated system temporary storage and removed after the operation.

Create a full encrypted archive:

```bash
npm run backup -- ./noema-backup.noema
```

Restore while Noema is stopped:

```bash
npm run restore -- ./noema-backup.noema /path/to/restored-data
```

A full `.noema` archive includes SQLite, encrypted mirrors, the installation master key, encrypted uploaded files/media, generated Links thumbnails, galleries, and other persistent data. The full archive is additionally encrypted with `NOEMA_BACKUP_PASSWORD`. Metadata JSON exports are portable but intentionally do not include binary contents.

## Main routes

| Route | Purpose |
|---|---|
| `/` | Task board and calendar |
| `/notes` | Notes |
| `/documents` | Documents and checklists |
| `/links` | Visual bookmarks, Cards/Table views, labels, and local thumbnails |
| `/files` | Private file library |
| `/ai-projects` | AI project catalog |
| `/buildingsite` | Project/site galleries |
| `/inspiration` | Reference galleries |
| `/stats` | Optional analytics dashboard |
| `/backup` | Metadata snapshots and backup downloads |
| `/openapi.json` | OpenAPI description |
| `/mcp` | MCP Streamable HTTP endpoint |
| `/healthz` | Health check |

## Roadmap: Noema Web/PWA + client-side E2EE

Client-side E2EE remains an optional future security layer, not a requirement for Noema's current encrypted-at-rest model. In a true E2EE design the server would never receive the plaintext encryption key, but this would significantly change server-side search, processing, thumbnails, and integrations.

See [E2EE_ROADMAP.md](E2EE_ROADMAP.md) for the proposed model and tradeoffs.
